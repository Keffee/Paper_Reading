TaylorMix Intro 行文需求

用于约束 Introduction 与后续 LaTeX 正文的写作风格、术语顺序和贡献口径。

总体原则

Intro 的目标读者是审稿人，不是作者自己。正文必须让不了解内部实验名、版本号、实现细节的人也能顺着读。
  • 行文采用逐步收窄的论证：数据分布影响 loss → online RLVR 中每步 batch 选择重要 → 数据管理视角下这是状态驱动的受约束选择查询 → 两类已有线索 → 两个缺口 → TaylorMix 的两层设计 → 理论确认 Taylor 对应关系 → 实验验证。
  • 语气要确定、克制、顶会论文式。不要像内部备忘录，也不要像在为近似方法辩解。
  • 每句话都要回答“为什么这句话现在出现”。不要突然抛出术语、版本名、实验指标或内部简称。
  • 结论段要有证据来源,但不重复具体表格数值。表后结论、章节结论和最终 Conclusion 可以使用 1).、2). 分点;每一点要写清楚“从表 X 可以看出”或“结合图 X 可以看出”,随后只写相对现象与机制解释,可以写“略高”“明显下降”“归零”“整体更均衡”等,但不要写具体指标值、delta、百分比、步数、样本数、模型规模或逐格报数;不要只写“由表 X 可以得到以下结论”这种空模板。具体数值留在表格和表格说明中。
  • 全文每个数学符号都要可追溯：读者应能从前文定义、当前公式上下文或明确配置项推出其含义。若某个符号首次出现,或不能由前文符号直接推出,必须在正文紧随其后用自然句解释其来源、含义和计算方式。
  • 正文负责让人读懂逻辑；灰色术语行可以放学名、引用备注、内部映射和后续实现细节。

叙事顺序

位置功能写作要求
① 痛点 说明为什么 online RLVR 中 batch composition 是重要数据选择问题。 只讲 batch 中的 training cases 决定 rollout、reward、更新方向；不要提前讲方法。
② 为什么是两层 从数据库/数据管理视角引出状态驱动的受约束选择查询。 正文说“每步从训练池里按约束选出 batch”；术语行再写 stateful constrained selection query。
③ 已有两类尝试 归纳领域/分布重分配与样本/候选重排两类线索。 候选类必须提到完整影响估计通常涉及 Hessian 逆或其近似；不要说所有方法精确求逆。
④ 两个缺口 提出领域边界解与候选更新风险两个缺口。 不要正式引出 TaylorMix；可用“本文方法”“完整版本”“风险项”等中性说法。
⑤ 本文方法 首次正式推出 TaylorMix。 采用“针对 A，TaylorMix 做 B，从而 C”的结构。每个“从而”后必须是目标或效果。
⑥ 为什么可信 说明理论确认 TaylorMix 两层选择对应 Taylor 一阶/二阶主项。 要写成确定性结论，不要写成“近似够用”的防守口吻。
⑦ 结果与贡献 总结新问题、两个挑战解决和实验性贡献。 贡献顺序：新问题 → 领域分配挑战 → 候选风险挑战 → 真实 RLVR 验证。

术语与首次出现

缩写

  • RLVR 首次正文出现写全：Reinforcement Learning with Verifiable Rewards。
  • GRPO 首次正文出现写全：Group Relative Policy Optimization。
  • KL 第一次用于正则时写成 KL 散度正则或 KL 散度正则化。

方法名

  • TaylorMix 在方法段正式引出。
  • 方法段之前避免写 TaylorMix Full；用“完整版本”“保留该风险项的版本”等。
  • 图里如果 legend 已经写 TaylorMix Full，正文图注仍可解释为“完整版本”。

数据对象

  • Intro 统一用 training cases / cases。
  • 不要在 intro 里频繁切换 prompt、sample、case。
  • “prompt”可在 Method 里解释为实现入口。

影响估计

  • 已有完整影响估计：可写 Hessian 逆或近似 Hessian 逆。
  • 我们的候选层：写低维二阶风险代理或低维候选风险实现。
  • 不要写“我们不需要 Hessian”这种容易被质疑的表述。

公式符号

  • 每个符号首次出现时必须说明来源：来自前文状态、当前候选集合、训练前配置、慢时钟缓存,还是理论接口。
  • 若符号由已有符号计算得到,正文要给出计算关系或文字口径,例如 rel_i 由 case 表示 h_i 与目标表示原型 p_\star 的余弦相似度计算；首次出现 p_c、p_\star 时必须说明 p 表示 prototype,不引入新的分数项。
  • 若符号是配置量或超参数,必须说明它是否固定、是否归一化、取值约束是什么。

风险与图

  • Intro 中的图只是“风险例子”，不是正式消融结论。
  • 不要写“消融日志例子”。用“风险例子”。
  • 图注要解释指标：actor gradient norm 写成“策略网络梯度范数”；KL jump 写成“策略 KL 跳变”。
  • 图的核心读法：去掉二阶风险项的版本出现梯度尖峰，完整版本没有超过触发线。
  • 不要使用“过尖”这种自造词。优先使用“不稳定更新”“梯度尖峰”“更新风险”。
  • 不要把 entropy 作为主风险论据，因为低 entropy 容易被解释成“更确定”。

方法段写法

Method 的目标读者仍然是审稿人，不是复现实验的工程同事。方法段不能写成实现清单或技术报告；每个设计都要先交代它解决哪个论文问题，再给出可执行定义，最后说明它带来的收益。
  • 方法章开头必须先承接 intro 已经敲定的两个缺口，再落到问题定义：为了解决 intro 中的领域边界分配和候选单步更新风险问题，TaylorMix 将定义 2 的 batch-composition query 具体化为……。不要把“TaylorMix 是定义 2 中 \(\operatorname{Select}_t\) 的实现”写成主句；定义 2 只是形式化接口，真正的写作重心是 TaylorMix 回答 intro 中的哪些问题。
  • 每个方法小节采用同一条逻辑链：为了 A，TaylorMix 做 B；具体地，定义/计算 C；从而 D。
  • A 必须是 intro、related work 或问题定义中已经提出的问题或挑战，例如领域边界解、候选更新风险、在线 batch 选择开销、GRPO 训练信号由 cases 决定。
  • B 是论文层面的设计动作，例如用 Taylor 一阶项做领域分配、用 KL 散度正则化分配、用低维二阶风险代理筛选候选。
  • C 才放公式、符号或算法细节。公式必须服务于上一句的设计目标，不要先扔公式再解释。
  • 第三章不只在开头承接 intro。每个 §3.x 小节的第一段都要说明它接住前文哪一环：§3.1 接定义 2 的两个控制量，§3.2 接“为什么用 Taylor 展开统一两个缺口”，§3.3 接领域边界解，§3.4 接候选单步更新风险，§3.5 接最终 batch 生成，§3.6 接在线反馈与下一步选择。
  • 小节开头不要写成元话语，例如“本节解释……”“本节接住……”“本节把……”。应改成承上启下的论文句：前半句明确接上一章/上一节已经建立的问题或变量，后半句自然引出当前小节要完成的设计动作。
  • 方法段不要写成“标签: 公式 + 其中”的技术报告形态，例如不要出现“GRPO 入口:”“一步效用:”“最终分数:”这类小标签。应先用论文正文句说明设计目的，再把关键公式单独成块展示，随后用自然句解释符号和收益。
  • 正文中的公式不能只依赖符号表。每个主公式第一次出现时,紧跟一句自然语言解释新符号,并说明这些符号能否由前文状态、前文公式或配置项推出；符号表只作总览,不能替代正文解释。
  • 抽象函数第一次出现时要交代输入空间、默认形式和选择原因。例如 \operatorname{dist} 不能只写“距离”,要说明它是在领域向量空间中计算、默认用余弦距离,以及为何适合当前设计。
  • 核心正则项不能只写公式。若正则项支撑主要贡献,必须说明它匹配哪个变量的几何结构、解决哪个缺口、相对显然替代方案有什么优势。
  • 公式中的选择对象要直观命名：本步 batch 统一写作 \mathcal{B}_t，领域内选中 cases 写作 \mathcal{B}_{c,t}，不要用 S_t 这类容易被误读为序列或状态集合的符号。
  • 方法段后面会反复使用的在线状态变量必须在 Preliminary / Problem Definition 中定义清楚，例如 \mathcal{H}_t 要先作为选择状态出现，再在方法段说明如何使用和更新。
  • D 必须是收益或目标，例如保留领域覆盖、避免过早边界分配、识别更高更新风险的 cases、支持每步在线运行。
  • 每个核心方法动作都要标明它承接哪个 Taylor 主项：领域分配承接一阶收益方向，候选风险代理承接二阶曲率风险，最终分数合成二者。
  • 每个核心方法动作都要标明由 §4 哪个 theorem 与 proof 校准：§4.1 先给出 Theorem 1 (Preview) 和 Theorem 2 (Preview) 概览 Taylor 对应关系，§4.2 给出 Proof of Theorem 1，对应领域成本和 KL 分配，§4.3 给出 Proof of Theorem 2，对应低维候选风险与候选筛选。
  • 小节之间要显式连接。章节顺序可以根据论文逻辑调整,但必须让读者看清:选择对象是什么、为什么要用 Taylor 展开、哪些设计承接一阶项、哪些设计承接二阶项、二者如何合成最终 batch、在线反馈如何进入下一步选择。
  • 方法段可以有公式，但公式数量服从逻辑。保留主公式，删掉只服务实现复现、且不能推进论文主张的符号。
  • Algorithm 要写成论文伪代码，而不是编号说明清单。应使用 Input、Output、for ... do、end for、必要的 if、sample、return、集合更新和 \leftarrow 赋值，让读者看到领域循环、候选循环、采样循环和状态更新的控制流。
  • Algorithm 中的采样过程要显式表达无放回：抽中一个 case 后从候选集合移除。采样算子命名保持直观，写 Softmax 即可，不使用 SeqSWOR、SoftmaxWOR 这类抽象名。
  • 正文引用 Algorithm 时优先引用语义动作或循环，例如“领域成本与配额循环”“候选评分与 softmax 采样循环”；避免依赖“第 5--6 步”这类脆弱行号引用，除非最终排版已经锁定。
  • 不要写代码路径、类名、版本名、刷新频率等技术报告信息。必要实现映射放灰色术语行，正文只保留读者理解方法所需的抽象机制。
  • 方法段每处理论引用都要说明它校准哪个方法动作：§4.2 校准领域成本与 Taylor 一阶下降方向，§4.3 校准低维候选风险与 Taylor 二阶曲率风险。
  • 避免把方法写成“我们先做 X，再做 Y，再做 Z”的流水账。每一步都要回答“为什么做、怎么做、做完有什么收益”。
  • 若使用 Taylor 展开或 oracle utility,必须先说明哪些量只是理论接口、哪些量是在线可观测代理。不要让读者误以为选择器在 rollout 前已经知道 g_t(\mathcal B)、\nabla M 或 \nabla^2M。
  • M 统一解释为训练期 selection target loss,并说明它与最终测试集隔离。不要在方法段含混地写“目标/验证 loss”而不解释其可访问性。

理论可信性写法

理论段要直接扣回 TaylorMix 的方法动作，而不是抽象地说“领域层”“候选层”。
  • 不要说“第 3 章的两层选择”，要说“TaylorMix 的两层选择”。
  • §4 必须按论文正文的定理证明结构展开：连续段落先交代 Taylor 展开、符号来源和方法动作，再给出 Theorem 1 (Preview)、Theorem 2 (Preview)、Proof of Theorem 1 与 Proof of Theorem 2。可见正文避免“说明/结论/标签 + 公式”的卡片式提纲。
  • §4 的段落之间必须有显式逻辑承接：上一段提出的读者问题,下一段要给出回答或推进；公式前说明为什么需要该公式,公式后说明它如何回到 TaylorMix 的领域分配、候选评分或采样动作。面向非本领域审稿人时,先用直观句解释一阶下降、二阶风险、曲率和 sketch,再给专业符号。
  • §4 与 §3 的 Taylor 符号必须一致：先固定任意训练步 t,说明下文省略时间下标,再写 \theta=\theta_t、g=\nabla M(\theta_t)、H=\nabla^2M(\theta_t)。Theorem 1 (Preview)、Theorem 2 (Preview) 及两个 proof 都必须从同一个 \mathcal T(u)=M(\theta)-M(\theta-\eta u) 出发；领域项优先直接写 \mathcal T(\widehat\mu_c),候选项优先直接写 \mathcal T(u_i),不要一个用 loss-change 方向、另一个用 utility 方向。
  • §3 和 §4 要尽量节省符号。同一意义不要前后换名：候选真实一阶项直接写 g^\top u_i,在线近似沿用 §3 的 U_i^{(1)}；参数空间二阶项直接写 u_i^\top H u_i,低维风险沿用 Curv_i^{op} 和 Curv_i^{sk}。不要再引入 V_i^{(1)}、Q_i、T_1/T_2、\widehat S_i^{\rm Tay} 等只起换名作用的符号。
  • 论文正文不得出现作者视角的穿帮语句,例如“对读者而言”“本章要说明”“下面先说明”“证明任务是”“直观地说”等。应改成论文内部的逻辑句,直接说明对象、问题、公式作用和结论。
  • 理论段避免画蛇添足的旁白句,例如“实际实现中的……”“这里的公式不要求……”“这条界的作用是……”“这个结论解释了为什么……”。需要表达的内容应直接写成论文结论,例如“低维曲率保留二阶风险排序”“该项作为候选分数中的二阶扣分项”。
  • 领域结论口径：理论确认 TaylorMix 的领域分配更新就是 Taylor 一阶项的分配求解。
  • KL 口径：KL 散度正则进一步把该信号转化为连续、可更新且保留覆盖的领域分配。
  • 候选结论口径：理论确认 TaylorMix 的低维候选风险实现与 hidden-residual 操作曲率一致；操作曲率是参数空间二阶项的可操作代理。
  • 理论证明必须把 Taylor 展开放在主语位置：先写清 M(\theta)-M(\theta-\eta u)、\eta g^\top u 和 \frac{\eta^2}{2}u^\top H u,再说明 Cost_c、Curv_i^{op}、Curv_i^{sk} 如何落到这些项上。不要把第 4 章写成脱离 Taylor 公式的代理指标合理性说明。
  • 数学证明不能把在线代理量直接当作真实 Taylor 项。若 Cost_c、U_i^{(1)}、Curv_i^{op} 或 Curv_i^{sk} 替代不可观测真量,正文必须给出校准条件、误差项或 surrogate 口径,并在最终排序/界中保留这些误差。
  • 不要把 Curv_i^{sk} 写成直接估计 \widehat\mu_i^\top\nabla^2M(\theta)\widehat\mu_i 或直接估计 Hessian。正确说法是：Curv_i^{sk} 低维近似 Curv_i^{op}，后者服务当前 batch 的二阶风险比较。
  • §4 末尾需要一个收束句,把 Theorem 1 与 Theorem 2 合回 TaylorMix 的两个方法动作,并自然接到系统部分:领域配额由一阶 loss 坐标驱动,候选采样由一阶有用性扣除二阶曲率风险驱动,后续系统分析围绕已校准的在线量展开。
  • 低维实现优势：它保留候选筛选所需的二阶风险相对关系，因此在保持风险筛选有效性的同时，足够高效地支持每步在线候选筛选。
  • 不要说“它不恢复每个样本的完整影响值”作为主句。若必须提，也要放在正向设计目标之后。
  • 不要把定理条件如“gap 足够大”塞进 intro；留给理论章。

系统设计写法

§5 要写成 SIGMOD/PACMMOD 系统论文中的 design section：先给系统边界，再给状态、刷新、一致性、恢复和开销边界。
  • §5 必须承接 §4 末尾的状态边界：系统嵌入围绕 Cost_c、U_i^{(1)} 和 Curv_i^{sk} 展开，不重新引入同义指标。
  • 开头先说明 TaylorMix 在 RLVR 流水线中的位置：位于 rollout 前，输入训练池、历史摘要和配置，输出本步 \mathcal B_t 的 case 索引；rollout、reward 计算和 GRPO 更新沿用原训练流程。
  • 系统设计不能停留在抽象原则。每节都要落到一次训练步中的具体对象和动作：case ID 队列、候选窗口、全局 batch ID 列表、worker 切片、reward 回流、checkpoint 保存项。
  • 系统章的主线应依次覆盖：online placement、state and refresh discipline、distributed consistency and recovery、cost and state bound。每一小节都要回答该设计解决哪类系统约束。
  • 状态表可以使用 SIGMOD 系统论文常见的 traceability 写法，但列名应服务论文论证，例如 State、Source、Refresh、Use in Selection；避免写成代码模块、类名、RPC 名或内部版本号清单。
  • 状态表的列名和内容要贴近运行过程，例如 Runtime Source、Written Back After、Concrete Use。不要只写“来源/刷新/用途”这种过宽泛的分类。
  • 刷新纪律要区分快变量和慢变量：reward EMA 随 rollout 回流，表示、sketch、anchors 和风险矩阵按慢时钟刷新。刷新频率如果没有实验或配置定稿，不在正文中写具体数字。
  • 分布式一致性要写成训练语义：一个逻辑选择器产生全局有序 case ID 列表，workers 接收该列表的不同切片；恢复时领域队列位置、候选窗口边界、随机投影、anchor 集、采样随机数状态和历史摘要随 checkpoint 继续。不要写具体 trainer 子类、worker RPC 或文件路径。
  • 开销分析可以引入复杂度符号，但首次出现必须立即解释，例如 n_t 表示本步实际打分的候选总数。复杂度口径要说明依赖领域数、候选窗口、sketch 维度和 anchor 数，而不是笼统写“开销很小”。
  • §5.4 的 cost/state bound 必须和替代路径放在同一张账单中比较，至少包括 oracle batch evaluation、全参数空间一阶候选分数、完整二阶或 influence/TRAK 式影响估计、TaylorMix sketch score。比较重点是 online work、state boundary 和适用角色。
  • 比较完整影响估计时要谨慎：可以说通常涉及 Hessian 逆或近似 Hessian 逆,适合作为离线分析、低频重排或实验基线；不要说所有方法都精确求 Hessian 逆,也不要用“我们不需要 Hessian”这类容易被质疑的表述。
  • 实测吞吐、显存、刷新频率和配置表应放到实验或实现细节表中；§5 正文先建立可验证的 state/cost bound。
  • 避免把 §5 写成“实现细节补丁”。正文需要说明这些机制如何让 §3 的选择器成为可 checkpoint、可复现、可分布式运行的 online batch-composition layer。

句式要求

  • 优先使用：针对 A，TaylorMix 做 B，从而 C。
  • 从而 后必须接目标或效果，不要只接实现细节。
  • 方法段优先使用：为了 A，TaylorMix 做 B；具体地 C；从而 D。
  • 避免连续使用“不是…而是…”这种 AI 味对比句。
  • 避免“只不过、只是、只需要、不恢复、没做完整”等削弱贡献的词。
  • 避免黑话堆叠。正文要先说人话，术语行再放专业名词。
  • 一句话中不要同时塞太多层级：领域、样本、Hessian、KL、Taylor、GRPO 不应无解释地挤在一起。
